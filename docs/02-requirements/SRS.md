## 1. บทนำ (Introduction)

### 1.1 วัตถุประสงค์
เอกสารนี้กำหนดความต้องการซอฟต์แวร์ (functional + non-functional) ของระบบ E-Learning สำหรับสภาทนายความแห่งประเทศไทย (LTC E-Learning) ฉบับ v1 เพื่อเป็นฐานของการออกแบบ (SDS), สเปก API, การทดสอบ (Test Plan) และการตรวจรับ กลุ่มผู้อ่าน: CTO/lead, ทีมพัฒนา, ผู้ทดสอบ, เจ้าหน้าที่ผู้รับมอบงานของสภาฯ

### 1.2 ขอบเขต (Scope)
ระบบเว็บ E-Learning ที่ระบบต้องรองรับ 6 ภารกิจหลักตาม Brief §1: (1) อบรมประชาชนทั่วไป (2) หลักสูตรต่อเนื่องสำหรับทนายความ (3) การสอบปลายหลักสูตรออนไลน์เพื่อรับประกาศนียบัตร (4) Credit Bank ตามรอบต่ออายุใบอนุญาต (5) ระบบบริหารจัดการโดยเจ้าหน้าที่ (6) UX ระดับสากลเหมาะกับบริบทไทย

**อยู่ในขอบเขต v1:** หลักสูตร self-paced (วิดีโอ + เอกสาร + quiz), การสอบปลายหลักสูตรออนไลน์, ประกาศนียบัตร + verify สาธารณะ, credit bank, ระบบสมาชิก/บัญชี, admin back-office, รายงาน/สถิติ, audit log, การแจ้งเตือนพื้นฐาน (ในระบบ + อีเมล)

**นอกขอบเขต v1:** ชำระเงินออนไลน์, คลาสสด (live), นำเข้า SCORM เต็มรูปแบบ, mobile native app (ทำ responsive web), AI assistant, การตรวจข้อสอบอัตนัยด้วยมือ (Brief v0.2.1 — รับ DCR แล้ว)

### 1.3 นิยามศัพท์
ใช้ศัพท์ตาม `docs/00-baseline/GLOSSARY.md ทั้งฉบับ (เช่น Course, Module, Lesson, Quiz, Final Assessment, Question Bank, Certificate, Credit, Credit Bank, Renewal Cycle, Credit Rule, License Number, Registrar, Audit Log, RLS, DCR) — ไม่นิยามซ้ำในเอกสารนี้

## 2. คำอธิบายภาพรวม (Overall Description)

### 2.1 บริบทผลิตภัณฑ์ (Product Context)
ระบบเป็นเว็บแอปพลิเคชันหนึ่งเดียว (Next.js 15 App Router + BFF `/api/v1` + Supabase) ให้บริการแก่:
- **ผู้เรียน (ประชาชน/ทนายความ)** — ผ่านเบราว์เซอร์ ทั้ง desktop และ mobile web
- **วิทยากร + เจ้าหน้าที่** — ผ่าน front-office เนื้อหาและ admin back-office ในระบบเดียวกัน (คุมด้วย RBAC)
- **ผู้ยืนยันประกาศนียบัตร (บุคคลทั่วไป/หน่วยงานภายนอก)** — ผ่านหน้า verify สาธารณะแบบไม่ต้องเข้าสู่ระบบ
- **ระบบภายนอก:** บริการอีเมล (ส่งแจ้งเตือน), บริการสื่อ (dev: Supabase local storage / prod: Cloudflare R2+Stream), CDN/WAF (prod: Cloudflare)
- **ข้อมูลอ้างอิงภายนอก:** เลขที่ใบอนุญาตว่าความ (นำเข้า/ตรวจโดยเจ้าหน้าที่ — วิธียืนยันรอ Q3)

### 2.2 ฟังก์ชันหลัก (ตามโดเมน Brief §5)
1. Identity & License — บัญชี โปรไฟล์ การผูกเลขที่ใบอนุญาต การยืนยันโดยเจ้าหน้าที่ บทบาท · 2. Catalog & Enrollment — หมวด/หลักสูตร ค้นหา รายละเอียด การลงทะเบียน เงื่อนไขเข้าเรียน · 3. Learning & Progress — โมดูล/บทเรียน (วิดีโอ เอกสาร quiz) ติดตามความคืบหน้า · 4. Assessment & Certification — question bank ชุดข้อสอบ กติกาสอบ ตรวจอัตโนมัติ ประกาศนียบัตร + QR verify
5. Credit Bank — กฎ credit, credit ledger (append-only), รอบต่ออายุ, ยอดสะสม, transcript · 6. Notification — แจ้งเตือนในระบบ + อีเมล (เทมเพลตภาษาไทย) · 7. Admin & Reporting — dashboard จัดการผู้ใช้/หลักสูตร/ข้อสอบ รายงาน export · 8. Audit — บันทึก action สำคัญทั้งหมด (append-only)

### 2.3 ลักษณะผู้ใช้ (User Characteristics — personas ตาม Brief §3)

| Persona | ลักษณะ + สมมติฐานการใช้งาน | บทบาทระบบ (RBAC seed) | ปริมาณโดยประมาณ |
| --- | --- | --- | --- |
| ประชาชน (Citizen) | ไม่มีบัญชีเดิม สมัครด้วย email/มือถือ ทักษะดิจิทัลหลากหลาย ต้องการง่ายและเป็นไทย | `guest` → `citizen` | ส่วนใหญ่ของ 100k ผู้ใช้ |
| ทนายความ (Lawyer) | มีเลขที่ใบอนุญาต เรียน+สอบ สะสม credit เพื่อต่ออายุใบอนุญาต | `lawyer` (ผูกใบอนุญาตแล้ว) | หลักหมื่นราย |
| วิทยากร (Instructor) | สร้าง/แก้เนื้อหาและ question bank ภายใต้การอนุมัติของเจ้าหน้าที่ | `instructor` (มักซ้อนกับ `lawyer`) | หลักร้อยราย |
| เจ้าหน้าที่ (Staff) | 4 ระดับ: ดูแลเนื้อหา / ดูแลการสอบ / นายทะเบียน (ออกประกาศนียบัตร) / ผู้ดูแลสูงสุด | `staff:viewer\|content\|exam\|registrar`, `super_admin` | หลักสิบราย |

พฤติกรรมข้ามบทบาท: บัญชีเดียวมีได้หลายบทบาท; บทบาทไม่สืบทอดเชิงลำดับชั้นอัตโนมัติ (ต้อง explicit — Brief §4); `super_admin` + `staff*` ต้องเปิด MFA

### 2.4 ข้อจำกัด (Constraints — binding)
- **C1 Stack (Brief §6):** Next.js 15 (App Router, RSC) + TypeScript strict + Tailwind; API = Route Handlers `/api/v1/*` + Server Actions; ตรวจ input ด้วย zod ทุกจุด; Supabase (PostgreSQL 15 + Auth + Storage) โดย RLS เปิดทุกตารางร่วมกับ RBAC; SQL migrations เป็นหลัก
- **C2 ห้าม hardcode ค่า environment-specific:** โค้ดชุดเดียวรันได้ทั้งสาม environment ต่างกันแค่ config/environment variables; สื่อ/อีเมลเข้าถึงผ่าน abstraction เท่านั้น
- **C3 การตรวจสอบย้อนกลับ:** audit log append-only บังคับด้วย DB privileges + RLS ห้ามมี API แก้/ลบ (D6)
- **C4 ภาษา:** Thai-first ทุก UI string (i18n-ready) error message เป็นภาษาที่ผู้ใช้เข้าใจ
- **C5 ความปลอดภัย/ความถูกต้องตามกฎหมาย:** OWASP ASVS L2 + PDPA (Brief §8 ทุกข้อ — ขยายใน SEC-001..016)
- **C6 Deployment (สาม environment):** dev = 100% local Docker (Supabase local stack) · staging = cloud preview (Vercel preview + Supabase staging + Cloudflare โดเมน staging, config ชุดเดียวกับ prod แยกด้วย env vars — ใช้พิสูจน์ PERF/SEC ตาม TEST-PLAN ก่อน promote) · prod = 100% cloud services (Vercel + Supabase Cloud + Cloudflare)
- **C7 ค่าทางธุรกิจที่ยังไม่ยืนยัน:** ต้องเป็น config พร้อม default + "รอยืนยัน Q#" ห้าม hardcode (D3)

### 2.5 สมมติฐานและ Dependency (Assumptions + Dependencies)
- **A1:** ผู้เรียนใช้เบราว์เซอร์สมัยใหม่ อินเทอร์เน็ตอย่างน้อย 4G · **A2:** บริการอีเมลขาออกมี SLA ตามผู้ให้บริการ — ระบบต้องมีคิว+retry (NTF-006) ไม่ assume ส่งสำเร็จทันที · **A3:** ยังไม่มี API ทางการของข้อมูลทนายความจากสภาฯ ใน v1 — ตรวจสอบแบบ manual (รอ Q3)
- **A4:** Cloudflare R2/Stream ใช้ได้ใน staging/prod และ quota เพียงพอต่อวิดีโอตาม Q6 · **A5:** เจ้าหน้าที่สภาฯ มีกระบวนการภายนอกระบบรองรับการอนุมัติ/เพิกถอนที่ระบบเสนอ · **A6:** คำตอบ Q1–Q6 จะมาถึงระหว่าง Wave C–E — ระบบจึงต้อง config-driven ตั้งแต่ต้น

## 3. ความต้องการเชิงหน้าที่ (Functional Requirements)

รูปแบบ: **ID · MoSCoW** — ระบบต้อง ... แล้ว AC เป็น bullet วัดได้

### 3.1 AUTH — การพิสูจน์ตัวตนและการเข้าถึงบัญชี

**AUTH-001 · M** — ระบบต้องรองรับการสมัครสมาชิกด้วยอีเมล พร้อมยืนยันอีเมลก่อนเปิดใช้งานบัญชี
- AC: สมัครด้วย email + รหัสผ่านที่ผ่านนโยบาย AUTH-006 ได้บัญชีสถานะ `pending_verification` ซึ่งเข้าสู่ระบบไม่ได้จนกว่าจะยืนยันอีเมลสำเร็จ
- AC: อีเมลยืนยันถูกส่งภายใน 60 วินาที ลิงก์หมดอายุ 24 ชม. ขอส่งใหม่ได้ภายใต้ rate limit (AUTH-011)
- AC: กรณี email ซ้ำกับบัญชีที่มีอยู่ API ตอบข้อความเดียวกับกรณีสมัครสำเร็จ (anti-enumeration) และส่งอีเมลแจ้งเจ้าของบัญชีเดิม

**AUTH-002 · M** — ระบบต้องรองรับการเข้าสู่ระบบด้วยอีเมล + รหัสผ่าน และการออกจากระบบ
- AC: เข้าสู่ระบบสำเร็จเมื่อข้อมูลถูกต้องและบัญชีไม่ถูกล็อก/ปิดใช้งาน ภายใน p95 ≤ 1 วินาที
- AC: การเข้าสู่ระบบผิดพลาดนับเข้า lockout (AUTH-009) และถูกบันทึกใน security event + audit · บัญชี staff*/super_admin/instructor ต้องผ่าน MFA (AUTH-007)

**AUTH-003 · S** — ระบบต้องรองรับการสมัคร/เข้าสู่ระบบด้วยเบอร์มือถือและรหัส OTP (default: เปิดเมื่อมี SMS provider — ระบุใน Appendix A)
- AC: OTP 6 หลัก หมดอายุ 5 นาที ตรวจความถูกต้องได้ครั้งละ 1 บัญชี และจำกัด 3 OTP/เบอร์/ชั่วโมง
- AC: เบอร์มือถือต้องผ่านการตรวจรูปแบบหมายเลขไทย (+66 / 0xxxxxxxxx)

**AUTH-004 · M** — ระบบต้องรองรับการตั้งรหัสผ่านใหม่กรณีลืมผ่านลิงก์จากอีเมล
- AC: token รีเซ็ตใช้ได้ 1 ครั้ง หมดอายุ 30 นาที และถูก invalidate ทันทีที่ใช้สำเร็จ · ตั้งรหัสใหม่สำเร็จแล้ว session ทั้งหมดถูกเพิกถอน + audit

**AUTH-005 · M** — ระบบต้องรองรับการเปลี่ยนรหัสผ่านของผู้ใช้ที่เข้าสู่ระบบอยู่ (ต้องกรอกรหัสปัจจุบัน)
- AC: เปลี่ยนสำเร็จ → ส่งอีเมลแจ้งเตือน + เพิกถอน session อื่นทั้งหมด + audit · รหัสใหม่ต้องผ่านนโยบาย AUTH-006 และห้ามซ้ำรหัส 3 ค่าล่าสุด

**AUTH-006 · M** — ระบบต้องบังคับนโยบายรหัสผ่าน (ค่าเป็น config — Appendix A)
- AC: ความยาว ≥ 12 ตัวอักษร (default) ผสมตัวอักษรพิมพ์ใหญ่/เล็ก/ตัวเลข/สัญลักษณ์อย่างน้อย 3 หมวด
- AC: ปฏิเสธรหัสผ่านที่อยู่ในรายการรหัสผ่านที่ถูกบุกรุกบ่อย (top common/leaked list) พร้อม error ภาษาไทยชี้เหตุผล

**AUTH-007 · M** — ระบบต้องบังคับ MFA (TOTP) สำหรับ `super_admin`, `staff` ทุกระดับ และ `instructor`
- AC: บัญชีบทบาทดังกล่าวต้องลงทะเบียน TOTP จนสำเร็จก่อนใช้งานฟังก์ชันอื่นของระบบ
- AC: มี backup code 8 รหัส ใช้ได้รหัสละครั้ง; ผู้ใช้ทั่วไป (citizen/lawyer) เปิด MFA ได้เองแบบ optional (instructor บังคับ)

**AUTH-008 · M** — ระบบต้องบริหาร session ตามนโยบาย (ค่าเป็น config)
- AC: idle timeout: เจ้าหน้าที่ (staff*/super_admin/instructor) 15 นาที · ผู้เรียน (citizen/lawyer) 60 นาที (default) หมดอายุแล้วต้องพิสูจน์ตัวใหม่ — idle timeout ไม่ใช่ absolute session lifetime (อายุสูงสุดของ session กำหนดแยกเป็น config)
- AC: refresh token rotation พร้อม reuse detection (ใช้ซ้ำ → เพิกถอนทั้งลำดับ) · ผู้ใช้มองเห็นรายการ session/อุปกรณ์ active ของตนเองได้

**AUTH-009 · M** — ระบบต้องล็อกบัญชีชั่วคราวเมื่อพยายามเข้าสู่ระบบผิดติดต่อกัน
- AC: ผิด 5 ครั้งใน 15 นาที → ล็อก 15 นาที (ค่า default — Appendix A) พร้อมแสดงเวลาที่เหลือแก่ผู้ใช้
- AC: เหตุการณ์ lockout ถูกบันทึกใน security event + audit โดยไม่เปิดเผยว่าบัญชีนั้นมีอยู่จริงหรือไม่ผ่านหน้าจอ

**AUTH-010 · M** — ระบบต้องรองรับการออกจากระบบของ session ปัจจุบัน และการออกจากระบบทุกอุปกรณ์
- AC: token ถูกเพิกถอนฝั่ง server ทันที (ไม่ใช่เพียงลบ cookie) · ปุ่มออกจากระบบเข้าถึงได้ภายใน 2 คลิกจากทุกหน้า

**AUTH-011 · M** — ระบบต้องจำกัดอัตราการเรียก (rate limit) ปลายทางยืนยันตัวตนทั้งหมด
- AC: login / ลืมรหัสผ่าน / OTP / ขอส่งอีเมลซ้ำ จำกัด 10 request/นาที/IP (default) เกินคือ HTTP 429 + ข้อความไทย
- AC: ใช้กลไกเดียวกันทั้ง dev (middleware) และ staging/prod (Cloudflare rate rule) — พฤติกรรมตรงกัน

### 3.2 IDENT — ตัวตน เนื้อหาประชาชน และการผูกใบอนุญาต

**IDENT-001 · M** — ระบบต้องให้ผู้ใช้ดูและแก้ไขโปรไฟล์ของตนเอง (ชื่อ-นามสกุล อีเมล เบอร์ติดต่อ)
- AC: ทุกฟิลด์ผ่าน zod; การเปลี่ยนอีเมลต้องยืนยันทางอีเมลใหม่ก่อนมีผล · บันทึกสำเร็จภายใน 2 วินาที + audit (ไม่บรรจุค่า PII ใน log)

**IDENT-002 · M** — ระบบต้องรองรับการยื่นคำขอผูกเลขที่ใบอนุญาตว่าความพร้อมเอกสารประกอบ
- AC: รับไฟล์แนบ jpg/png/pdf ≤ 10 MB/ไฟล์ เก็บผ่าน storage abstraction (signed URL ไม่ public)
- AC: เลขที่ใบอนุญาตผ่านการตรวจรูปแบบ; คำขอสถานะ `pending`; วิธียืนยันตาม config Q3 (default: เจ้าหน้าที่ตรวจ)

**IDENT-003 · M** — ระบบต้องให้เจ้าหน้าที่ที่ได้รับมอบหมายพิจารณาคำขอผูกใบอนุญาต (อนุมัติ/ปฏิเสธพร้อมเหตุผล)
- AC: การปฏิเสธต้องระบุเหตุผล (บังคับ) และทุกคำตัดสินบันทึก ผู้ตัดสิน/เวลา/เหตุผล ลง audit
- AC: ผู้ยื่นได้รับแจ้งผลทางแจ้งเตือนในระบบ + อีเมลภายใน 5 นาทีหลังตัดสิน

**IDENT-004 · M** — ระบบต้องเพิ่มบทบาท `lawyer` ให้บัญชีโดยอัตโนมัติเมื่อคำขอผูกใบอนุญาตได้รับการอนุมัติ
- AC: บทบาทปรากฏและใช้สิทธิ์ได้ภายใน 5 วินาทีหลังอนุมัติ เป็น explicit grant (ไม่ใช่ implication) · บันทึกใน audit อ้างอิงคำขอและผู้อนุมัติ

**IDENT-005 · M** — ระบบต้องแสดงสถานะการยืนยันตัวตนของผู้ใช้ต่อเจ้าของ และให้ยื่นคำขอใหม่ได้หลังถูกปฏิเสธ
- AC: หน้าสถานะแสดง สถานะ/เหตุผลการปฏิเสธ/เวลาพิจารณา; ยื่นซ้ำได้ไม่จำกัดครั้ง (ภายใต้ rate limit upload)

**IDENT-006 · M** — ระบบต้องให้ `super_admin` เท่านั้นแต่งตั้ง/ถอดบทบาท `instructor` และ `staff:*` รายบุคคล
- AC: การมอบบทบาท staff* ทำได้เฉพาะเมื่อบัญชีนั้นเปิด MFA สำเร็จแล้ว; ทุกการเปลี่ยนบทบาทถูก audit

**IDENT-007 · M** — ระบบต้องรองรับบัญชีเดียวที่มีหลายบทบาทพร้อมกัน
- AC: สิทธิ์ที่ได้ = union ของบทบาทที่ถูกมอบแบบ explicit เท่านั้น ตรวจสอบด้วย integration test กรณีทนายความที่เป็นวิทยากร

**IDENT-008 · M** — ระบบต้องรองรับสิทธิของเจ้าของข้อมูลตาม PDPA: เข้าถึง/ส่งออกข้อมูลของตน ขอลบบัญชี และจัดการ consent
- AC: ขอส่งออกข้อมูล (JSON) ได้เองและได้รับไฟล์ภายใน 24 ชม.; การลบบัญชีเป็น soft-delete ตาม retention policy (SEC-012) พร้อม audit
- AC: หน้า consent แสดงรายการข้อมูลส่วนบุคคลที่ระบบเก็บพร้อมวัตถุประสงค์ และบันทึกสถานะ consent ทุกครั้งที่เปลี่ยน

### 3.3 CAT — หมวดหลักสูตรและการค้นพบหลักสูตร

**CAT-001 · M** — ระบบต้องรองรับการสร้าง/แก้ไข/จัดลำดับหมวดหลักสูตร (CRUD) โดย `staff:content`
- AC: หมวดมีรหัส unique + ชื่อ + คำอธิบาย + ลำดับแสดงผล; ลบได้เฉพาะเมื่อไม่มีหลักสูตรอ้างอิง (ไม่มีให้ archive) · ทุกการเปลี่ยนแปลงถูก audit

**CAT-002 · M** — ระบบต้องแสดงรายการหลักสูตรที่เผยแพร่แก่ผู้เยี่ยมชมทั่วไป (guest) แบบแบ่งหน้า
- AC: หน้าละ 20 รายการ (default) แสดง ชื่อ/หมวด/ชั่วโมงเรียน/credit/กลุ่มเป้าหมาย; โหลดเสร็จ ≤ 2 วินาที (PERF-007) · เข้าถึงได้โดยไม่ต้องเข้าสู่ระบบ

**CAT-003 · M** — ระบบต้องรองรับการค้นหาและกรองหลักสูตร
- AC: ค้นด้วยคีย์เวิร์ด (ชื่อ/คำอธิบาย รองรับภาษาไทย+อังกฤษ) และกรองด้วย หมวด/กลุ่มเป้าหมาย/สถานะเปิดรับ รวมเงื่อนไขแบบ AND ได้
- AC: ผลลัพธ์กลับมา p95 ≤ 2 วินาที ที่ชุดข้อมูลทดสอบ 5,000 หลักสูตร

**CAT-004 · M** — ระบบต้องแสดงหน้ารายละเอียดหลักสูตรแก่ guest
- AC: แสดง คำอธิบาย โครงสร้างโมดูล/บทเรียน ชื่อวิทยากร จำนวนชั่วโมง credit ที่จะได้รับ เงื่อนไขสอบ (จำนวนครั้ง เกณฑ์ผ่าน เวลา) และจำนวนผู้ลงทะเบียน
- AC: มีปุ่ม "ลงทะเบียน" ที่นำผู้ใช้ที่ยังไม่เข้าสู่ระบบไปสู่การสมัคร/เข้าสู่ระบบก่อน แล้วกลับมาหลักสูตรเดิม

**CAT-005 · M** — ระบบต้องบริหารวงจรชีวิตหลักสูตร: draft → pending_review → published → archived
- AC: เฉพาะ `staff:content` อนุมัติ published; instructor สร้าง/แก้ได้เฉพาะหลักสูตรที่ได้รับมอบหมายและยังไม่ published; ทุกการเปลี่ยนสถานะถูก audit พร้อมผู้อนุมัติ
- AC: หลักสูตรที่ถูก archive: ผู้ลงทะเบียนเดิมยังเข้าเรียนต่อได้ แต่ลงทะเบียนใหม่ไม่ได้และไม่แสดงในผลค้นหาสาธารณะ

**CAT-006 · M** — ระบบต้องให้ instructor จัดการโครงสร้างหลักสูตร (โมดูล/บทเรียน/ลำดับ/ประเภทเนื้อหา: วิดีโอ เอกสาร quiz)
- AC: จัดลำดับโมดูล/บทเรียนได้ (ปุ่มขึ้น-ลงหรือ drag); บทเรียนต้องมีเนื้อหาอย่างน้อย 1 รายการก่อนส่งตรวจ
- AC: การแก้เนื้อหาหลัก published ต้องสร้างเวอร์ชันใหม่และผ่านการอนุมัติใหม่ก่อนแสดงต่อผู้เรียนรายใหม่

**CAT-007 · M** — ระบบต้องรองรับการกำหนดกลุ่มเป้าหมายของหลักสูตร (สาธารณะ / เฉพาะ `lawyer`)
- AC: ผู้ไม่มีบทบาทตรงตามเงื่อนไขมองเห็นรายละเอียดได้แต่ลงทะเบียนไม่ได้ พร้อมข้อความอธิบายเงื่อนไขเป็นภาษาไทย

### 3.4 LRN — การเรียนและความคืบหน้า

**LRN-001 · M** — ระบบต้องรองรับการลงทะเบียนเรียนหลักสูตรที่เผยแพร่และเปิดรับอยู่
- AC: ลงทะเบียนสำเร็จด้วยการกระทำเดียว (1 คลิก) หลังผ่านการตรวจสิทธิ์; ซ้ำเป็น idempotent (ไม่สร้างซ้ำ/ไม่ error ต่อผู้ใช้) · สร้าง record สถานะ `active` + audit

**LRN-002 · M** — ระบบต้องแสดงรายการ "หลักสูตรของฉัน" พร้อมความคืบหน้าและทางเข้าเรียนต่อ
- AC: แสดง % ความคืบหน้าต่อหลักสูตร เรียงล่าสุดได้; เข้าสู่บทเรียนที่ค้างอยู่ได้ภายใน 2 คลิก

**LRN-003 · M** — ระบบต้องรองรับการเรียนบทเรียนประเภทวิดีโอ
- AC: เล่นผ่าน signed URL ที่หมดอายุตาม config (default 15 นาที) ไม่เปิด URL ตรงแบบถาวร; ปรับคุณภาพตามแบนด์วิดท์
- AC: บันทึกตำแหน่งเล่นล่าสุด; การ seek ข้ามช่วงไม่ถูกนับเป็นเวลาดูจริง (นำไปใช้ใน LRN-008)

**LRN-004 · M** — ระบบต้องรองรับการเรียนบทเรียนประเภทเอกสาร (PDF)
- AC: แสดงในหน้าเว็บผ่าน viewer โดยไม่บังคับดาวน์โหลด; อนุญาตดาวน์โหลดเฉพาะเมื่อหลักสูตรเปิดตัวเลือก (config)

**LRN-005 · M** — ระบบต้องรองรับการทำแบบทดสอบย่อย (quiz) ปลายบทเรียน
- AC: ตรวจและแสดงผลทันทีพร้อมคะแนน เฉลย และคำอธิบาย; ทำซ้ำได้ไม่จำกัดครั้ง (config) โดยเก็บผลทุกครั้ง · คะแนนที่ใช้ประเมินเงื่อนไขผ่านบทเรียนคือคะแนนสูงสุด (default, config ได้)

**LRN-006 · M** — ระบบต้องบันทึกความคืบหน้าการเรียนระดับบทเรียน
- AC: server เป็นผู้ตัดสินเงื่อนไขผ่านเพียงผู้เดียว (ค่าจาก client เป็นข้อมูลดิบ); เก็บเวลาเรียนสะสมต่อบทเรียน · แสดงผลอัปเดตภายใน 5 วินาทีหลังเงื่อนไขผ่านถูกตัดสิน

**LRN-007 · M** — ระบบต้องคำนวณและแสดงความคืบหน้ารวมของหลักสูตร (รายโมดูล + รวมทั้งหลักสูตร)
- AC: สูตร = จำนวนบทเรียนที่ผ่านเงื่อนไข / จำนวนบทเรียนทั้งหมดที่บังคับ (นิยามรายละเอียดและตารางที่ SDS/Data Dictionary)

**LRN-008 · M** — ระบบต้องตัดสินเงื่อนไขผ่านบทเรียนตาม config ต่อหลักสูตร
- AC: วิดีโอ: เวลาเล่นจริง ≥ 80% ของความยาว (`video_complete_pct` default); เอกสาร: เปิดชมจนครบเงื่อนไขการเข้าถึงที่ระบบกำหนด; quiz: คะแนน ≥ 60% (default)
- AC: เปลี่ยนค่าเกณฑ์ได้โดยไม่กระทบผลการตัดสินที่เกิดขึ้นแล้ว

**LRN-009 · M** — ระบบต้องรองรับการกลับมาเรียนต่อ (resume) จากจุดที่ค้างไว้
- AC: กลับสู่บทเรียนและตำแหน่งวิดีโอล่าสุดได้ภายใน 2 คลิกจาก "หลักสูตรของฉัน"; ทำงานข้ามอุปกรณ์เมื่อใช้บัญชีเดียวกัน

**LRN-010 · S** — ระบบต้องรองรับเงื่อนไขการเข้าเรียนเพิ่มเติม (เช่น ต้องผ่านหลักสูตรพื้นฐานก่อน)
- AC: ตรวจเงื่อนไขก่อนอนุญาตการลงทะเบียน พร้อมข้อความบอกเหตุผลและลิงก์หลักสูตรที่ต้องผ่าน

### 3.5 ASM — การสอบและธนาคารข้อสอบ

**ASM-001 · M** — ระบบต้องรองรับ CRUD ธนาคารข้อสอบ (question bank) สำหรับ instructor/`staff:exam`
- AC: รองรับประเภทข้อสอบ: ปรนัยเลือกตัวเดียว / เลือกหลายตัว / ถูก-ผิด; ข้อมูลครบ: โจทย์ ตัวเลือก คำตอบ คะแนน คำอธิบายเฉลย ระดับความยาก
- AC: ทุก input ผ่าน zod; การลบเป็น soft delete เพื่อคงความถูกต้องของการสอบที่ผ่านมา; audit ทุกการเปลี่ยนแปลง

**ASM-002 · M** — ระบบต้องรองรับการจัดกลุ่ม/tag ข้อสอบตามหลักสูตร โมดูล และหมวด
- AC: กรองข้อสอบตามกลุ่ม/tag ได้เมื่อสร้างชุดข้อสอบ; ข้อสอบที่เคยถูกใช้ในการสอบที่จบแล้วจะแก้คำตอบ/โจทย์ไม่ได้ (ต้องสร้างเวอร์ชันใหม่)

**ASM-003 · M** — ระบบต้องรองรับการสร้างชุดข้อสอบปลายหลักสูตรจาก question bank
- AC: กำหนดต่อหลักสูตร: จำนวนข้อ (แยกตามกลุ่ม) คะแนนเต็ม เวลา จำนวนครั้ง เกณฑ์ผ่าน — ทั้งหมดเป็น config
- AC: ชุดข้อสอบต้องได้รับอนุมัติจาก `staff:exam` ก่อนใช้งาน; มี versioning; audit ทุกการแก้ไข

**ASM-004 · M** — ระบบต้องสุ่มข้อสอบให้ผู้เรียนแต่ละคน/แต่ละครั้ง
- AC: สุ่มเลือกข้อจาก pool ตามกฎชุดข้อสอบ + สลับลำดับข้อ + สลับลำดับตัวเลือก (ยกเว้นประเภทที่มีลำดับความหมาย)
- AC: ผู้สอบ 2 คนในหลักสูตรเดียวกันได้ชุด/ลำดับที่แตกต่างกัน (ตรวจได้ด้วยการทดสอบ); เก็บข้อมูลชุดที่สุ่มได้ (รวม seed/ลำดับ) เพื่อการทบทวน

**ASM-005 · M** — ระบบต้องจำกัดเวลาสอบตามที่กำหนดต่อชุดข้อสอบ (default 60 นาที — รอยืนยัน Q2)
- AC: แสดงเวลานับถอยหลังที่เห็นชัด; เวลาอ้างอิงนาฬิกาฝั่ง server
- AC: หมดเวลาแล้วระบบ submit อัตโนมัติฝั่ง server ไม่ว่า client จะยังเปิดอยู่หรือไม่

**ASM-006 · M** — ระบบต้องจำกัดจำนวนครั้งการสอบต่อหลักสูตร (default 3 ครั้ง — รอยืนยัน Q2)
- AC: ระหว่างครั้งมี cooldown default 24 ชม.; แสดงจำนวนครั้งที่เหลือก่อนเริ่มสอบ · ครบจำนวนแล้วเริ่มสอบใหม่ไม่ได้ พร้อมช่องทางติดต่อเจ้าหน้าที่

**ASM-007 · M** — ระบบต้องตัดสินผลผ่าน/ไม่ผ่านตามเกณฑ์ (default ≥ 70% — รอยืนยัน Q2)
- AC: แสดงผล ผ่าน/ไม่ผ่าน พร้อมคะแนนทันทีหลัง submit

**ASM-008 · M** — ระบบต้องบันทึกคำตอบระหว่างสอบอัตโนมัติ
- AC: auto-save ทุก 15 วินาที (default) และทุกครั้งที่ผู้เรียนเปลี่ยนคำตอบ; server เป็น source of truth
- AC: เมื่อ refresh/disconnect แล้วกลับเข้ามาภายใน 5 นาที ต้องได้คำตอบล่าสุดและเวลาสอบที่เดินมาแล้วเช่นเดิม

**ASM-009 · M** — ระบบต้องตรวจข้อสอบปรนัยทุกประเภทโดยอัตโนมัติทันทีที่ submit
- AC: คะแนนถูกต้อง 100% เทียบ answer key (พิสูจน์ด้วย unit test ครอบคลุมทุกประเภทข้อสอบ); ไม่มีขั้นตอนตรวจด้วยมือใน v1

**ASM-010 · M** — ระบบต้องแสดงและแจ้งผลสอบ
- AC: แสดง คะแนน ผล ครั้งที่ เวลา ณ ผล; ส่งแจ้งเตือน+อีเมลภายใน 5 นาที (NTF-002) · เก็บข้อมูลข้อสอบจริงที่ได้รับ (ชุดสุ่ม) เพื่อการทบทวนและ audit

**ASM-011 · S** — ระบบต้องมีมาตรการ anti-cheat พื้นฐาน (ขอบเขตรอยืนยัน Q4)
- AC: สุ่มข้อ+ตัวเลือก (ASM-004) + จำกัดเวลา (ASM-005) + ห้ามบัญชีเดียวสอบพร้อมกัน 2 session (session ใหม่ถูก block)
- AC: ตรวจจับการสลับแท็บ/หน้าต่างระหว่างสอบ (visibility event) และบันทึกเป็น event ประกอบการสอบ; default ไม่มีการบันทึกหน้าจอ/กล้อง/ไม่ระงับการสอบอัตโนมัติ

**ASM-012 · S** — ระบบต้องรองรับการทบทวนข้อสอบหลังสอบ (config ต่อหลักสูตร)
- AC: เมื่อเปิดใช้: ผู้เรียนดูข้อที่ตอบ คำตอบถูก/ผิด เฉลย และคำอธิบายของครั้งที่เลือกได้
- AC: default แสดงได้เฉพาะเมื่อสิ้นสุดโอกาสสอบทั้งหมดหรือผ่านแล้ว (ไม่เปิดระหว่างยังมีครั้งเหลือ)

**ASM-013 · M** — ระบบต้องบังคับเงื่อนไขเข้าสอบก่อนเริ่มสอบ
- AC: ตรวจฝั่ง server ว่าผ่านบทเรียนครบตามเงื่อนไขหลักสูตร (default: บังคับ; config ต่อหลักสูตร) และมีสิทธิ์ครั้งสอบเหลืออยู่

**ASM-014 · M** — ระบบต้องเก็บและแสดงประวัติการสอบ
- AC: ผู้เรียนเห็นประวัติของตนทุกครั้ง (วันเวลา คะแนน ผล ระยะเวลาที่ใช้); `staff:exam` เห็นรายบุคคล + สถิติข้อสอบ (อัตราตอบผิดต่อข้อ)

### 3.6 CRT — ประกาศนียบัตร

**CRT-001 · M** — ระบบต้องตรวจเงื่อนไขคุณสมบัติรับประกาศนียบัตรโดยอัตโนมัติ
- AC: เงื่อนไข: ผ่านการสอบตามเกณฑ์ + การลงทะเบียนยัง valid + (หลักสูตรของทนาย) บัญชีผูกใบอนุญาตแล้ว · หน้าหลักสูตรแสดงสถานะคุณสมบัติ (ครบ/ยังไม่ครบ พร้อมเหตุผล)

**CRT-002 · M** — ระบบต้องให้ `staff:registrar` (นายทะเบียน) เป็นผู้ออกประกาศนียบัติ
- AC: แสดงรายชื่อผู้มีสิทธิ์รอออก; ออกได้ทีละรายหรือเป็นชุด (bulk); ทุกการออกถูก audit พร้อมผู้ออก

**CRT-003 · M** — ระบบต้องออกประกาศนียบัตรที่มีรหัสอ้างอิง unique และ QR code
- AC: รหัสตามรูปแบบ config: `LTC-<ปี ค.ศ.>-<สุ่ม 6 หลัก>` ไม่ซ้ำ เดายาก (ยืนยันรูปแบบแล้ว; แสดงผลปี พ.ศ. ได้ตาม I18N-003 — รอยืนยันการใช้งานกับสภาฯ) · ข้อมูลบนใบ: ชื่อผู้รับ หลักสูตร วันที่ออก จำนวน credit; QR ชี้หน้า verify (CRT-004)

**CRT-004 · M** — ระบบต้องมีหน้ายืนยันความถูกต้องประกาศนียบัตร (verify) สาธารณะ
- AC: เข้าถึงได้โดยไม่ต้องเข้าสู่ระบบ; แสดง รหัส หลักสูตร วันที่ออก สถานะ (valid/revoked/superseded) · ไม่แสดงอีเมล เลขที่ใบอนุญาต หรือ PII อื่น; จำกัดอัตราการค้น; รหัสไม่ถูกต้องตอบข้อความเดียวกันทุกกรณี

**CRT-005 · M** — ระบบต้องให้เจ้าของดาวน์โหลดประกาศนียบัตรเป็นไฟล์ PDF
- AC: ไฟล์มีรหัส+QR ตรงกับฐานข้อมูล; ขนาดกระดาษ A4 ตาม design system; ดาวน์โหลดได้เฉพาะเจ้าของและ registrar

**CRT-006 · M** — ระบบต้องรองรับการเพิกถอนประกาศนียบัตร
- AC: กระทำได้โดย registrar ขึ้นไป พร้อมเหตุผลบังคับ; สถานะเปลี่ยนเป็น `revoked` และหน้า verify แสดง revoked + วันที่
- AC: credit ที่ได้จากใบนั้นต้องถูกปรับผ่าน credit ledger (CRB-007); แจ้งเจ้าของ + audit

**CRT-007 · S** — ระบบต้องรองรับการออกประกาศนียบัตรใหม่แทนใบเดิม (re-issue)
- AC: ใบใหม่มีรหัสใหม่และอ้างอิงแทนใบเดิม; ใบเดิมเปลี่ยนสถานะ `superseded`; ประวัติทั้งสองใบถูกเก็บครบ

**CRT-008 · S** — ระบบต้องรองรับโหมดออกประกาศนียบัตรอัตโนมัติ (default: ปิด — รอ registrar อนุมัติทุกใบ)
- AC: เมื่อเปิด: ออกอัตโนมัติภายใน 5 นาทีหลังผู้เรียนผ่านเงื่อนไข; audit ระบุโหมดที่ใช้ ณ เวลาออก

### 3.7 CRB — Credit Bank

**CRB-001 · M** — ระบบต้องจัดเก็บกฎ credit เป็น configuration (ไม่ hardcode)
- AC: กำหนดต่อหลักสูตร: จำนวน credit ประเภท อายุ/เงื่อนไขการใช้; แก้ไขได้โดย `super_admin`/ผู้ได้รับมอบหมาย + audit
- AC: การแก้กฎมีผลกับเหตุการณ์ที่เกิดใหม่เท่านั้น (ไม่คำนวณย้อนหลัง) เว้นแต่ระบุ explicitly ผ่าน adjustment (CRB-007)

**CRB-002 · M** — ระบบต้องเก็บ credit ledger แบบ append-only
- AC: ทุกรายการมี ผู้เกี่ยวข้อง/เหตุการณ์/เวลา/จำนวน (+/−)/เหตุผล/อ้างอิง (certificate/attempt)
- AC: ห้าม UPDATE/DELETE บังคับด้วย DB privileges + RLS; การแก้ยอดทำได้เพียงสร้างรายการปรับ (adjustment) ใหม่เท่านั้น

**CRB-003 · M** — ระบบต้องบันทึก credit โดยอัตโนมัติเมื่อผู้เรียนผ่านหลักสูตร
- AC: สร้าง ledger entry ตามกฎที่มีผล ณ วันผ่าน ภายใน 5 นาที; idempotent (certificate/ผลผ่านหนึ่งรายการ = credit หนึ่งชุด ไม่ซ้ำซ้อน)
- AC: ความถูกต้องของการคำนวณมี unit test ครอบคลุม (รวมกรณีเปลี่ยนกฎ + เพิกถอนใบ)

**CRB-004 · M** — ระบบต้องคำนวณรอบต่ออายุ (Renewal Cycle) ของผู้ใช้แต่ละราย (ค่ารอบรอยืนยัน Q1)
- AC: กำหนดรอบต่อบุคคลจากวันที่กำหนดตาม config (default: รายปี นับจากวันที่อนุมัติการผูกใบอนุญาต) · ผู้ใช้มองเห็นรอบปัจจุบัน/ถัดไป; การเปลี่ยน config ไม่ย้อนแปลงรอบที่ปิดแล้ว

**CRB-005 · M** — ระบบต้องแสดงยอด credit สะสมต่อรอบต่ออายุ
- AC: แสดง ได้รับแล้ว / ต้องมี / ขาดอีก ต่อรอบปัจจุบัน คำนวณจาก ledger (ตรวจย้อนกลับได้ทุกยอด) และแสดงประวัติยอดรายรอบที่ผ่านมา

**CRB-006 · M** — ระบบต้องจัดทำ transcript รายบุคคล
- AC: รวม หลักสูตรที่ผ่าน วันที่ จำนวน/ประเภท credit สถานะ; ดูออนไลน์ + ดาวน์โหลด PDF/CSV · เจ้าหน้าที่ที่ได้รับมอบหมายเรียกดูได้ตามสิทธิ์ (audit การเข้าถึง — SEC-013)

**CRB-007 · M** — ระบบต้องรองรับการปรับปรุง credit โดยเจ้าหน้าที่
- AC: การปรับ (เพิ่ม/ลด/โอนรอบ) ต้องมีเหตุผลบังคับ + ผู้อนุมัติ; สร้าง adjustment entry ใน ledger (ไม่แก้รายการเดิม); แจ้งเจ้าของ + audit

**CRB-008 · S** — ระบบต้องรองรับกฎอายุ/การนับ credit ข้ามรอบ (default: ไม่สะสมข้ามรอบ — รอยืนยัน Q1)
- AC: การคำนวณใช้กฎที่ config ไว้ ณ รอบนั้น; มี unit test กรณี credit หลายรอบ + ข้ามปี

### 3.8 NTF — การแจ้งเตือน

**NTF-001 · M** — ระบบต้องมีการแจ้งเตือนภายในระบบ (notification inbox)
- AC: เหตุการณ์ขั้นต่ำ: ผลสอบ การออก/เพิกถอนประกาศนียบัตร ผลการพิจารณาใบอนุญาต; แสดงสถานะอ่าน/ยังไม่อ่าน + badge จำนวน

**NTF-002 · M** — ระบบต้องส่งอีเมลแจ้งผลสอบ (เทมเพลตภาษาไทย)
- AC: ส่งสำเร็จภายใน 5 นาทีหลังผล; มีคะแนน ผล และครั้งที่; ผ่านระบบเทมเพลตกลาง (ไม่ hardcode ข้อความใน logic)

**NTF-003 · M** — ระบบต้องส่งอีเมลเมื่อประกาศนียบัตรถูกออก/เพิกถอน
- AC: มีลิงก์ดาวน์โหลด PDF และลิงก์หน้า verify; ส่งภายใน 5 นาทีหลังเหตุการณ์

**NTF-004 · S** — ระบบต้องแจ้งเตือนรอบต่ออายุใกล้หมดแก่ผู้ใช้ `lawyer` (ขึ้นกับ Q1)
- AC: ส่งก่อนครบรอบ 60/30/7 วัน (config); ระบุยอด credit ปัจจุบันและที่ยังขาด

**NTF-005 · C** — ระบบต้องให้ผู้ใช้ตั้งค่าการรับแจ้งเตือนรายประเภท/ช่องทางได้
- AC: เปิด-ปิดได้รายประเภท ยกเว้นธุรกรรมบังคับ (ความปลอดภัยบัญชี/ผลคำตัดสินของเจ้าหน้าที่) ที่ส่งเสมอ

**NTF-006 · M** — ระบบต้องส่งอีเมลผ่านคิวแบบ asynchronous พร้อม retry
- AC: retry 3 ครั้ง ถอยหลังแบบ exponential; บันทึกสถานะการส่งทุกฉบับ; ล้มเหลวต่อเนื่องต้องแจ้งผู้ดูแลระบบ (OPE-003)

### 3.9 ADM — การบริหารจัดการและรายงาน

**ADM-001 · M** — ระบบต้องมี dashboard สถิติสำหรับเจ้าหน้าที่
- AC: KPI ขั้นต่ำ: ผู้ใช้ใหม่/รวม การลงทะเบียน ผลสอบ (ผ่าน/ไม่ผ่าน) credit ที่ออก; กรองช่วงวันที่ได้ · ตัวเลขอัปเดตล่าช้าไม่เกิน 15 นาที; เข้าถึงเฉพาะ staff ขึ้นไป

**ADM-002 · M** — ระบบต้องรองรับการจัดการผู้ใช้โดยเจ้าหน้าที่
- AC: ค้นหาด้วย ชื่อ/อีเมล/สถานะ; ดูรายละเอียด+บทบาท; ปิด/เปิดใช้งานบัญชีพร้อมเหตุผล (audit)
- AC: ขอบเขตสิทธิ์ตาม sub-role (viewer ดูอย่างเดียว); การดูโปรไฟล์ผู้อื่นถูก audit (SEC-013)

**ADM-003 · M** — ระบบต้องรองรับรายงานการเรียน/ผลสอบ/credit
- AC: รายงาน: ความคืบหน้ารายหลักสูตร ผลสอบรายบุคคล/หลักสูตร ยอด credit; กรองช่วงเวลา/หลักสูตร/บุคคล · แสดงผลเสร็จ ≤ 10 วินาที ที่ 100,000 ผู้ใช้

**ADM-004 · M** — ระบบต้องรองรับการ export รายงานเป็น CSV
- AC: UTF-8 with BOM (เปิดใน Excel แล้วภาษาไทยถูกต้อง); 1 แถวต่อระเบียน; ทดสอบที่ 10,000 แถว ≤ 60 วินาที (PERF-008) · ฟิลด์ที่ export จำกัดตามสิทธิ์ผู้ขอ + audit

**ADM-005 · M** — ระบบต้องรองรับการจัดการหลักสูตรโดย `staff:content`
- AC: เห็นทุกหลักสูตรทุกสถานะ; อนุมัติ/ส่งกลับให้แก้ไขพร้อมความเห็น; ประวัติการอนุมัติถูก audit

**ADM-006 · S** — ระบบต้องรองรับการติดตามการสอบโดย `staff:exam`
- AC: แสดงจำนวน/สถิติการสอบ (กำลังดำเนินการ/เสร็จ) แบบ aggregate; สถิติข้อสอบ (อัตราตอบผิดต่อข้อ) · ไม่แสดงคำตอบรายบุคคล real-time ระหว่างสอบ (ความเป็นส่วนตัว)

### 3.10 AUD — บันทึกตรวจสอบ (Audit Log)

**AUD-001 · M** — ระบบต้องบันทึก audit log ทุก action สำคัญ
- AC: เหตุการณ์ขั้นต่ำ: การเข้าสู่ระบบ/ความล้มเหลวการยืนยันตัว/lockout การเปลี่ยนรหัสผ่าน+MFA การเปลี่ยนบทบาท การพิจารณาใบอนุญาต publish/ถอดหลักสูตร การแก้ question bank/ชุดข้อสอบ ผลสอบ การออก/เพิกถอนประกาศนียบัตร credit adjustment การเข้าถึงข้อมูลส่วนบุคคล การ export การเปลี่ยน config
- AC: ทุกรายการมี actor/action/target/timestamp (UTC + แสดงผลไทย)/IP/result; การเปลี่ยนแปลงข้อมูลสำคัญโดยไม่มี audit ต้องเป็นไปไม่ได้ (ตรวจด้วย integration test)

**AUD-002 · M** — ระบบต้องบังคับ audit log เป็น append-only
- AC: ไม่มี API/UI/DB privilege ใดแก้หรือลบ; บังคับระดับ DB (revoke UPDATE/DELETE + RLS) — ทดสอบด้วยการพยายาม UPDATE/DELETE แล้วต้อง fail

**AUD-003 · M** — ระบบต้องรองรับการค้นหา/กรอง audit log โดยเจ้าหน้าที่ที่ได้รับมอบหมาย
- AC: กรอง actor/ประเภทเหตุการณ์/ช่วงเวลา/target; ผลลัพธ์ ≤ 10 วินาที ที่ 1 ล้านแถว แบ่งหน้าได้ · การค้นหา audit ถูกบันทึกใน audit ด้วย (self-auditing)

**AUD-004 · M** — ระบบต้องไม่บรรจุ PII ใน audit payload
- AC: ห้าม เลขบัตรประชาชน อีเมล เลขที่ใบอนุญาต ในทุก log — อ้างอิงด้วย user_id; ตรวจบังคับด้วย automated scan ใน CI (SEC-007)

**AUD-005 · M** — ระบบต้องเก็บ audit log ตามนโยบาย retention (default ≥ 5 ปี — Appendix A)
- AC: การลบตามอายุทำผ่านกระบวนการที่ได้รับอนุมัติและถูก audit; ค่า retention เป็น config

## 4. ความต้องการนอกหน้าที่ (Non-Functional Requirements)

### 4.1 PERF — สมรรถนะ

**PERF-001 · M** — ระบบต้องรองรับผู้ใช้จดทะเบียนสะสม ≥ 100,000 ราย โดยไม่ต้องปรับโครงสร้างข้อมูลหลัก
- AC: load test ชุดข้อมูล 100,000 accounts + 1,000,000 enrollment ยังตอบสนองตาม PERF-004

**PERF-002 · M** — ระบบต้องรองรับผู้เรียนพร้อมกัน ≥ 10,000 sessions
- AC: load test 10,000 VU (ดูวิดีโอ+ส่ง progress) นาน ≥ 30 นาที: error rate < 0.1% และ p95 ตาม PERF-004

**PERF-003 · M** — ระบบต้องรองรับผู้สอบพร้อมกัน ≥ 5,000 คน
- AC: 5,000 simultaneous exam sessions: auto-save ไม่สูญหาย, submit สำเร็จ, ผลออกภายใน 60 วินาทีหลัง submit

**PERF-004 · M** — ระบบต้องมีเวลาตอบสนอง API: p95 ≤ 500 ms (read) และ p95 ≤ 1,000 ms (write) ที่โหลด 500 req/s
- AC: วัดจาก load test บน staging (ที่พิสูจน์ตาม TEST-PLAN) + monitoring จริงใน prod (OPE-001); ค่าเป้าเป็น config ของ monitoring alert

**PERF-005 · M** — ระบบต้องมี Core Web Vitals ของหน้าหลัก: LCP ≤ 2.5 วินาที และ INP ≤ 200 ms บนเครือข่าย 4G
- AC: วัดด้วยเครื่องมือ RUM/lighthouse ใน CI ต่อหน้าหลัก 5 หน้า (หน้าแรก รายการหลักสูตร รายละเอียด เรียน สอบ)

**PERF-006 · S** — ระบบต้องเริ่มเล่นวิดีโอภายใน 3 วินาที (p75) บน 4G
- AC: วัดบน staging ผ่าน CDN/streaming ตาม TEST-PLAN; วิดีโอให้บริการผ่าน CDN ไม่ผ่าน origin โดยตรง

**PERF-007 · M** — ระบบต้องคืนผลค้นหาหลักสูตรภายใน p95 ≤ 2 วินาที ที่ 5,000 หลักสูตร
- AC: ทดสอบพร้อมคีย์เวิร์ดไทย+อังกฤษและตัวกรองรวมกัน

**PERF-008 · S** — ระบบต้องสร้างไฟล์ export 10,000 แถวภายใน 60 วินาที
- AC: ทดสอบรายงานผลสอบขนาด 10,000 แถว; กระบวนการทำงานแบบ background + แจ้งเตือนเมื่อเสร็จ

### 4.2 SEC — ความมั่นคงปลอดภัยและความเป็นส่วนตัว (ขยาย Brief §8 ทุกข้อ)

**SEC-001 · M** — ระบบต้องเป็นไปตาม OWASP ASVS Level 2 และ OWASP Top 10
- AC: ทบทวน design ตาม checklist ASVS V1–V14; ผลการทดสอบ (ZAP + manual pass บน staging ตาม TEST-PLAN) ต้องไม่มีช่องโหว่ระดับ high/critical ค้างอยู่ก่อน release

**SEC-002 · M** — ระบบต้องเปิด RLS ทุกตารางใน PostgreSQL ร่วมกับ RBAC
- AC: ทุกตารางมี policy; integration test ยืนยันว่า anon/authenticated อ่านข้อมูลข้างผู้ใช้/ข้ามสิทธิ์ไม่ได้

**SEC-003 · M** — ระบบต้องใช้ DB roles แบบ least-privilege
- AC: `service_role` ใช้เฉพาะ server-side (BFF) เท่านั้น; anon ไม่มีสิทธิ์เขียนตรงต่อตารางธุรกิจ; ตรวจเป็นข้อบังคับ code review

**SEC-004 · M** — ระบบต้องบังคับ append-only ของ audit log ด้วย DB privileges + RLS (มุมความปลอดภัยของ AUD-002)
- AC: บทบาทใด ๆ ในระบบ (รวม service_role ของแอป) ต้องไม่มีสิทธิ์ UPDATE/DELETE audit log

**SEC-005 · M** — ระบบต้องมี rate limiting และ WAF ทุกสภาพแวดล้อม
- AC: staging/prod = Cloudflare WAF + rate rules; dev = middleware เทียบเคียงได้; ปลายทางบังคับ: auth, verify สาธารณะ, export, API ทั่วไป; เกินเกณฑ์ตอบ 429

**SEC-006 · M** — ระบบต้องเก็บ secrets เฉพาะ environment variables เท่านั้น
- AC: ห้าม commit ห้าม log ทุก environment; CI มี secrets scan เป็น merge gate; ไม่มีค่า default credential ในโค้ด

**SEC-007 · M** — ระบบต้องไม่ log ข้อมูล PII (เลขบัตรประชาชน เลขที่ใบอนุญาต อีเมล)
- AC: log ผ่าน serializer ที่ตัด PII; อ้างอิงบุคคลด้วย user_id; CI มี automated scan หา PII pattern ใน log statement

**SEC-008 · M** — ระบบต้องบังคับ MFA + session timeout + lockout แก่บัญชีบริหารและวิทยากร
- AC: ยึด AUTH-007/008/009; ทดสอบว่าบัญชี staff*/super_admin/instructor ที่ไม่มี MFA ใช้งานฟังก์ชันอื่นไม่ได้

**SEC-009 · M** — ระบบต้องยืนยันประกาศนียบัตรต่อสาธารณะได้โดยไม่เปิดเผย PII เกินจำเป็น
- AC: ยึด CRT-004; ตรวจสอบ response ของหน้า verify/API ว่าไม่มีฟิลด์นอกเหนือที่ระบุ

**SEC-010 · M** — ระบบต้องเก็บข้อมูลส่วนบุคคลน้อยที่สุดตามหลัก PDPA พร้อม consent
- AC: ทุกฟิลด์ส่วนบุคคลมีเหตุผลการเก็บใน Data Dictionary; ข้อมูล optional เก็บเมื่อมี consent; มีหน้าแจ้งเก็บ-ใช้-เปิดเผย

**SEC-011 · M** — ระบบต้องรองรับสิทธิเจ้าของข้อมูล PDPA (เข้าถึง แก้ไข ลบ โอนย้าย)
- AC: ยึด IDENT-008; คำขอที่ต้องดำเนินการโดยเจ้าหน้าที่มี SLA ตอบ ≤ 30 วันและบันทึกการดำเนินการ

**SEC-012 · M** — ระบบต้องมี data retention policy รายประเภทข้อมูล
- AC: กำหนดอายุเก็บทุกประเภท (เช่น audit ≥ 5 ปี, บัญชีที่ขอลบ = soft-delete ตามอายุคงค้างตามกฎ); กระบวนการลบตามอายุถูก audit

**SEC-013 · M** — ระบบต้องบันทึกการเข้าถึงข้อมูลส่วนบุคคล (PDPA access log)
- AC: เจ้าหน้าที่เปิดดูโปรไฟล์/transcript ผู้อื่น = รายการ audit แยกประเภทชัดเจน ค้นหาได้ตาม AUD-003

**SEC-014 · M** — ระบบต้องตรวจ input ด้วย zod ทุกขอบเขตรับข้อมูล (route handler, server action, query param)
- AC: ทุก endpoint มี schema; negative/fuzz test ยืนยันปฏิเสธ input ผิดรูปแบบด้วยข้อความไทยที่ชี้เหตุผล

**SEC-015 · M** — ระบบต้องบังคับ HTTPS พร้อม security headers
- AC: HSTS, CSP (อนุญาตเฉพาะแหล่งที่จำเป็น), X-Content-Type-Options, X-Frame-Options DENY (ยกเว้นหน้าที่ต้อง embed ตาม design); ผลตรวจ security headers ผ่านเกณฑ์

**SEC-016 · M** — ระบบต้องปกป้องข้อมูลส่วนบุคคลที่จัดเก็บ (at rest / in transit)
- AC: transport = TLS ทุกสภาพแวดล้อม; เอกสารยืนยันใบอนุญาตเข้าถึงผ่าน signed URL อายุสั้นเท่านั้น; DB at-rest encryption ตามผู้ให้บริการ (Supabase); ไม่เก็บความลับในคอลัมน์แบบ plain; region ตาม Q5

### 4.3 REL — ความน่าเชื่อถือ

**REL-001 · M** — ระบบต้องมี availability ≥ 99.9% ต่อเดือน (ไม่นับ maintenance window ที่แจ้งล่วงหน้า)
- AC: วัดจาก monitoring (OPE); รายงาน availability รายเดือน

**REL-002 · M** — ระบบต้องมีการสำรองข้อมูลอัตโนมัติ: RPO ≤ 24 ชม. และ RTO ≤ 4 ชม.
- AC: backup รายวันอัตโนมัติ + บันทึกผล; ซ้อม restore ทุกไตรมาสและเก็บหลักฐาน

**REL-003 · S** — ระบบต้องแยกความล้มเหลวของบริการเสริมไม่ให้กระทบธุรกรรมหลัก
- AC: อีเมลล่ม → การเรียน/สอบ/ออกประกาศนียบัตรยังทำงานได้ (แจ้งเตือนค้างในคิว); CDN/streaming มี fallback ตามผู้ให้บริการ

**REL-004 · M** — ระบบต้องรักษาความต่อเนื่องของการสอบเมื่อผู้เรียนขาดการเชื่อมต่อชั่วคราว
- AC: ยึด ASM-008; นาฬิกาสอบเดินตาม server ต่อเนื่องไม่หยุดระหว่าง disconnect

### 4.4 USA — ความใช้งานง่าย (Usability)

**USA-001 · M** — ระบบต้องใช้ภาษาไทยเป็นหลักในทุกหน้าจอของผู้ใช้
- AC: ไม่มี UI string อังกฤษลอยนอกศัพท์เทคนิคตาม Glossary; ทุกข้อความมาจาก message catalog (I18N-001)

**USA-002 · M** — ระบบต้องใช้งานได้บนหน้าจอ 360–1920 px (responsive)
- AC: งานหลัก (สมัคร ลงทะเบียน เรียน สอบ) ทำสำเร็จบนมือถือ 360 px ได้ครบทุกขั้นตอน

**USA-003 · S** — ระบบต้องให้ทำภารกิจหลักสำเร็จภายใน ≤ 5 คลิก (สมัคร → ลงทะเบียน → เริ่มเรียน)
- AC: ทดสอบ journey จริงบน prototype/ระบบ และนับคลิก

**USA-004 · M** — ระบบต้องแสดง error message ภาษาไทยที่อธิบายสาเหตุและวิธีแก้
- AC: ไม่แสดง raw error code/stack ต่อผู้ใช้ปลายทาง; ข้อความผ่าน message catalog

**USA-005 · S** — ระบบต้องให้ผู้ใช้ใหม่สมัครเสร็จสมบูรณ์ภายใน 3 นาที (median)
- AC: usability test ผู้ทดสอบ ≥ 5 คน วัดเวลาจริง

### 4.5 I18N — การแปลภาษา

**I18N-001 · M** — ระบบต้องเก็บ UI string ทั้งหมดใน message catalog แบบ i18n-ready (next-intl-style)
- AC: ไม่มี hardcode string ใน component; lint rule หรือ review checklist บังคับ

**I18N-002 · S** — ระบบต้องรองรับการสลับภาษาไทย (default) / อังกฤษ
- AC: v1 ครอบคลุมหน้าสาธารณะ+การเรียน+การสอบ; admin back-office เป็นไทยเท่านั้น (ระบุขอบเขตชัด)

**I18N-003 · M** — ระบบต้องฟอร์แมตวันที่/เวลา/ตัวเลขตาม locale
- AC: ไทย default (แสดงปี พ.ศ. ในหน้าผู้ใช้ไทย พร้อมเลือก ค.ศ. ได้ในโปรไฟล์); ระบบภายในเก็บ UTC

**I18N-004 · S** — ระบบต้องไม่พังเลย์เอาต์เมื่อสลับภาษา (ข้อความยาวต่างกัน)
- AC: ทดสอบหน้าหลักด้วย string ยาวสุดของทั้งสองภาษา

### 4.6 ACC — การเข้าถึงได้ (Accessibility)

**ACC-001 · M** — ระบบต้องเป็นไปตาม WCAG 2.1 ระดับ AA สำหรับเนื้อหาสาธารณะและเส้นทางเรียน/สอบหลัก
- AC: automated scan (axe) 0 critical violation + ตรวจด้วยมือตาม checklist ต่อหน้าหลัก

**ACC-002 · M** — ระบบต้องใช้งานฟังก์ชันหลักได้ด้วยคีย์บอร์ดล้วน
- AC: สมัคร เรียน ทำ quiz สอบ ครบวงจรด้วยคีย์บอร์ด; focus มองเห็นชัดเจนทุก interactive element

**ACC-003 · M** — ระบบต้องมี contrast ratio ≥ 4.5:1 ของข้อความปกติ
- AC: ตรวจด้วยเครื่องมือทุกสีหลักของ design system

**ACC-004 · S** — ระบบต้องมีข้อความทางเลือกของสื่อ
- AC: รูปมี alt ที่มีความหมาย; วิดีโอบทเรียนมีเอกสาร transcript ภาษาไทยแนบ (เป็นข้อมูลบังคับของบทเรียนวิดีโอ)

### 4.7 MAINT — การบำรุงรักษาได้ (Maintainability)

**MAINT-001 · M** — ระบบต้องพัฒนาด้วย TypeScript strict โดยไม่ใช้ `any` โดยไม่จำเป็น
- AC: `tsc --strict` ผ่านเป็น merge gate; lint บังคับ/เตือน `any`

**MAINT-002 · M** — ระบบต้องใช้โค้ดชุดเดียวทั้งสาม environment (dev Docker / staging cloud / prod cloud) ต่างกันเฉพาะ config
- AC: ไม่มีเงื่อนไข environment กระจายใน business logic; สื่อ/อีเมล/คิวเข้าถึงผ่าน abstraction; smoke test parity ครบทั้งสาม environment

**MAINT-003 · M** — ระบบต้องเปลี่ยนแปลง schema ผ่าน SQL migration เท่านั้น
- AC: ทุกการเปลี่ยน schema อยู่ใน `supabase/migrations`; รันซ้ำได้บน local Docker จนสำเร็จ

**MAINT-004 · M** — ระบบต้องมี unit test ของ business logic หลัก ≥ 80% coverage
- AC: ครอบคลุม module: credit calculation, assessment grading, progress rules, RBAC helpers; วัดใน CI

**MAINT-005 · S** — ระบบต้องมีการสแกนช่องโหว่ dependency ใน CI
- AC: lockfile บังคับ; รายงาน vulnerability เป็นส่วนหนึ่งของ pipeline

**MAINT-006 · M** — ระบบต้องบังคับ merge gates: lint + tsc + tests + build + secrets scan
- AC: CI บล็อก merge เมื่อ gate ใดไม่ผ่าน; โค้ดกลุ่ม auth/security/data ต้องผ่าน codex gate เพิ่ม (โครงการ rule 5)

### 4.8 OPE — การดำเนินงานและเฝ้าระวัง (Operations)

**OPE-001 · M** — ระบบต้องมี structured logging พร้อม correlation ID ทุก request
- AC: ไล่ตาม request ข้าม component ได้ด้วย ID เดียว; log level ปรับได้ผ่าน config; ไม่มี PII ใน log (SEC-007)

**OPE-002 · M** — ระบบต้องมี health check endpoint ตรวจสถานะ dependency หลัก
- AC: `/api/health` ตรวจ app + database + storage/email queue และตอบภายใน 2 วินาที; ใช้โดย monitoring

**OPE-003 · M** — ระบบต้องแจ้งเตือนผู้ดูแลเมื่อเกินเกณฑ์ (alerting)
- AC: เกณฑ์ขั้นต่ำ: error rate, latency (PERF-004), availability, คิวอีเมลล้มเหลวต่อเนื่อง; แจ้งผ่านช่องทางที่ config

**OPE-004 · S** — ระบบต้องมี runbook การ deploy/rollback
- AC: เอกสาร runbook + ซ้อม rollback อย่างน้อย 1 ครั้งก่อนเปิดใช้จริง

## 5. ความต้องการอินเทอร์เฟซภายนอก (External Interface Requirements)

### 5.1 UI (ผู้ใช้ปลายทาง)
- เว็บแอปพลิเคชัน responsive ผ่านเบราว์เซอร์สมัยใหม่ 2 เวอร์ชันล่าสุดของ Chrome/Safari/Edge/Firefox
- ออกแบบตาม Design System (worker-5) โดยหลัก Thai-first, WCAG 2.1 AA (ACC-001), รองรับ 360–1920 px
- ทางเข้าหลัก: หน้าสาธารณะ (ค้นหาหลักสูตร) / ผู้เรียน / วิทยากร / admin back-office — คุมด้วย RBAC เดียวกัน

### 5.2 API (`/api/v1`)
- REST + JSON ผ่าน Next.js Route Handlers ภายใต้ prefix `/api/v1/*`; input ตรวจด้วย zod ทุก endpoint (SEC-014)
- การพิสูจน์ตัวตนใช้ session ที่ Supabase Auth ออกให้; การอนุญาตใช้ RBAC + RLS สองชั้น
- error response มีรูปแบบเดียวกันทั้งระบบ (code + ข้อความไทย); pagination แบบ cursor; versioning ผ่าน prefix
- กลุ่มปลายทางตามโดเมน (รายละเอียดเต็มอยู่ที่ API Spec ของ worker-4): `/api/v1/auth/*`, `/api/v1/profile*`, `/api/v1/license*`, `/api/v1/categories*`, `/api/v1/courses*`, `/api/v1/enrollments*`, `/api/v1/lessons*`+progress, `/api/v1/question-banks*`, `/api/v1/exams*`+attempts, `/api/v1/certificates*`, `/api/v1/verify/*` (สาธารณะ), `/api/v1/credits*`+transcripts, `/api/v1/notifications*`, `/api/v1/admin/*`, `/api/v1/audit*`, `/api/health`

### 5.3 อีเมล (ขาออก)
- เข้าถึงผ่าน email abstraction เท่านั้น (C2): dev = SMTP/กล่องจดหมายจำลองใน Docker; staging/prod = ผู้ให้บริการ cloud ที่เลือกตาม config
- เทมเพลตภาษาไทยจากระบบเทมเพลตกลาง (NTF-002/003/004); ส่งผ่านคิว + retry (NTF-006); ห้าม PII เกินจำเป็นในเนื้อหา

### 5.4 การเก็บสื่อ (Storage abstraction)
- dev = Supabase local storage (Docker); staging/prod = Cloudflare R2 (ไฟล์/เอกสาร) + Cloudflare Stream (วิดีโอ) — โค้ดเรียกผ่าน interface เดียว ห้ามอ้าง provider ตรงใน business logic (C2)
- ไฟล์เอกสารยืนยัน: private + signed URL อายุสั้น (SEC-016); วิดีโอ: signed URL + ไม่เปิด direct download (default ตาม Q6); ข้อจำกัดความยาว/ความละเอียด/ขนาดไฟล์เป็น config (Appendix A)

### 5.5 หน้า verify สาธารณะ (รับผู้ใช้ภายนอก)
- URL ตามรหัสประกาศนียบัตร/QR; ไม่ต้องเข้าสู่ระบบ; จำกัดอัตราค้น; ข้อมูลที่แสดงตาม CRT-004 เท่านั้น
